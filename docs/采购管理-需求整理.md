## 〇、已确认结论

1. **审核链路**：村室发起 → 成员机构审核 → 中心药房终审；成员机构发起 → 中心药房审核；中心药房发起 → 无需审核（提交即生效）。
2. **旧页面处置**：现有 purchase-request*（采购申请）升级改造为「采购需求」，复用 purchase-common.js / styles.css。
3. **菜单可见角色**：村室 → 仅「采购需求」；成员机构 → 「采购需求 + 采购计划」；中心药房 → 三个菜单全部可见；HIS 对接人员不可见整个采购管理。
4. **线稿形式**：可交互 HTML 线稿，按现有 styles.css 组件风格实现。

## 三、采购计划

### 3.1 发起采购计划（purchase-plan-create.html）

**基本信息区**：申请机构只读、申请库位下拉、**配送地址下拉（默认选中默认地址，必填）**、申请说明选填、提交人/提交时间默认登录人。

> 配送地址来源：该机构的配送地址库（见 3.3），保存时写入 `addressId` + 地址快照 `address`，历史单据不随地址库后续修改而变化。

**药品明细区**
- 明细列：药品名称、药品编码、药品规格、生产企业、**基药（是/否）**、**计划数量（用户录入）**、**单价（用户录入）**、**总价（系统计算 = 数量 × 单价）**
- 批量添加筛选项：药品种类、「库存低于下限」

**关联采购需求（核心特性）**
- 支持直接关联**已审批通过**的采购需求，可关联单个 / 多个
- 合并规则：**同一药品 + 同一规格 + 同一生产企业** → 计划数量自动累加
- 累加后计划数量仍支持用户手动修改

### 3.3 配送地址维护（purchase-plan.html → 页头「配送地址维护」）

- **粒度**：整单一个配送地址（不做明细级分地址）。
- **归属**：地址库按**机构**隔离（`org`），机构之间不可见、互不影响；数据存 `PC_ADDRESSES`。
- **多条 + 唯一默认**：同一机构可维护多条地址，其中恰好一条为默认；默认地址在新建采购计划时自动带入。
- **入口**：采购计划列表页页头「配送地址维护」按钮 → 右侧抽屉 620px。
- **抽屉内容（v1.7 简化为「一行 = 输入框 + 默认地址勾选」）**
  - 打开抽屉直接就是地址列表，**没有「列表页 / 表单页」两种视图切换**；提示「当前机构 / 共 N 条地址 / 默认地址自动带入 / 修改后点保存生效」。
  - **每条地址直接就是一个输入框**（≤100 字，预填现有地址），不做「先点文本、再变输入框」的两步交互；输入即写入草稿。
  - 输入框右侧为「默认地址」复选框（单选语义：勾选一条自动取消其他；取消当前默认会被还原并提示「需保留一条默认地址」），再右侧为「删除」文字按钮。
  - **「＋ 新增地址」虚线按钮紧跟地址列表下方**（不放在抽屉底部），点击后在列表末尾追加一行空输入框并自动聚焦。
  - 抽屉底部固定「取消 / 保存」：修改、新增、勾选默认、删除**都只改草稿**，点「保存」才真正写入；点「取消」直接放弃关闭；X / 遮罩 / Esc 关闭时若有未保存修改会二次确认；输入框内回车等同保存。
- **规则**
  - 地址即一段文本，直接作为上报省平台的 `distributeAddr` 使用；100 字上限与接口 `varchar(100)` 对齐，避免提交时超长被拒。
  - 始终保留恰好一条默认地址：取消勾选当前默认会被还原；删除默认地址后自动把第一条转正。
  - 新增第一条地址时自动成为默认。
  - 保存时校验：地址不能为空（空地址输入框标红并聚焦提示），至少保留一条地址。
  - 地址变更只影响之后新建的采购计划，已提交/已审核的计划保留原地址快照。

> v1.3 调整：原先的四级省市区街道级联 + 收货人/电话/备注全部去掉，改为「一个文本框输入地址」。省平台药品接口 H006 的 `distributeAddr` 本身就是一段文本，收货人信息不在对接字段内，故不必在院内维护。

## 四、采购订单

### 4.1 订单列表（purchase-order.html）

数据来源：**同步省药品招采平台采购订单**（本 demo 用 mock 数据模拟）。

**一行 = 一条订单明细**：同一订单的「省平台订单号 / 采购计划单号」用 `rowspan` 合并，其余列逐条明细展示。

**列口径（v1.3）**：只展示省平台接口返回的字段，**不展示药品名称 / 规格 / 生产企业 / 数量 / 单价 / 金额**等药品类字段。

| 列 | 级别 | 说明 |
|---|---|---|
| 省平台订单号 | 订单 | 同订单合并；H005/H008 `orderId` |
| 采购计划单号 | 订单 | 同订单合并；院内侧关联的计划单号（`JH...`），一个订单可关联多个计划时逐行列出，无关联显示「—」 |
| 订单提交时间 | 订单 | v1.6 恢复；同订单合并。H005/H006 订单级提交时间（`submitTime`），本 demo 排序也以此为准 |
| 订单明细编号 | 明细 | H006 返回、H008/H009/H015 入参的 `orderDetailId`；形如 `PROV202611010001-01`，全局唯一，是配送明细的挂靠主键 |
| 订单明细状态 | 明细 | H008 `orderDetailState`，圆点 + 文字，按状态着色（见 4.4） |
| 响应时间 | 明细 | H008 `confirmTime`（配送商响应时间），未响应显示「—」 |
| 响应原因 | 明细 | H008 `refuseReason`（配送商拒绝响应理由）；拒绝配送 / 未及时配送等说明也展示在此；超出列宽省略 + hover 显示全文 |
| 操作 | 明细 | 仅「查看配送明细」（不带次数角标） |

> 表头横向排布（v1.6）：省平台订单号 → 采购计划单号 → 订单提交时间 → 订单明细编号 → 订单明细状态 → 响应时间 → 响应原因 → 操作；表格 8 列、`min-width: 1090px`，1440 及以上无横向滚动，响应原因列吸收剩余宽度。
>
> **表格视觉（v1.4 调整）**：本表**关闭隔行斑马纹**（合并单元格跨行，隔行变色会把同一订单切成两截）；订单级列（省平台订单号、采购计划单号、订单提交时间）铺浅灰蓝底衬 + `rowspan` 合并，与白色底的明细行形成两个视觉层级；订单之间用 1px 分割线，订单内明细不画线。
>
> v1.3 移除：药品名称 / 药品规格 / 生产企业 / 数量 / 单价 / 金额列，以及操作列的「关联采购计划」入口（改为「采购计划单号」列直接呈现关联结果）。v1.6 按需求方要求恢复订单提交时间列。

**订单无明细时**：仍显示订单行，明细区展示「暂无订单明细」。

**筛选**（v1.6）：订单号（模糊查询）、采购计划单号（模糊查询，订单关联的任一计划单号命中即保留该订单）、订单明细状态（任一明细命中即保留该订单；选中状态时**只列命中的明细行**，分页文案追加「仅列该状态明细」）。

**分页**：按订单分页（每页 10 个订单），分组不被截断；文案为「共 N 个订单 · M 条明细」。

### 4.2 采购计划关联

订单与采购计划的关联关系以「采购计划单号」列直接呈现（同订单合并），不再提供「关联采购计划数」点击数入口与关联编辑弹窗（v1.3 按需求方要求移除）。

> 订单与计划的关联数据仍保留在 `PC_ORDERS.planIds` 与 `PC_PLANS.linkedOrderIds`，后续如需要可在计划侧或订单详情页恢复入口。

### 4.4 订单明细状态字典（`orderDetailState`）

来源：省医药采购平台与配送企业系统对接技术标准。**各省字典不一致**（部分省仅「待发货/已发货/已收货/已作废」共 4 态），因此实现为可配置字典 `PC.ORDER_STATE`，页面不写死文案；换省只改字典。

| 码 | 状态 | 码 | 状态 |
|---|---|---|---|
| 0 | 已保存待提交 | 5 | 拒绝配送 |
| 1 | 已提交待响应 | 6 | 未及时配送 |
| 2 | 已响应待配送 | 7 | 收货中 |
| 3 | 拒绝响应 | 8 | 已收货 |
| 4 | 已配送待收货 | 9 | 已撤单 |

状态着色：4 / 7 主色（待办中）、8 绿色（完成）、3 / 5 / 6 红色（异常）、0 / 1 / 9 灰色（中性）、2 次要文字色。

**本期范围**：仅展示状态，由省平台同步回传，不在本系统做收货/拒收/撤单的状态流转（后续迭代再议）。

### 4.5 配送明细（订单明细 1 : n）

**关系**：一条订单明细可被供应商**多次配送**（分批发货），每次配送是一条配送明细；订单明细 : 配送明细 = 1 : n。

**入口**：列表操作列「查看配送明细」→ 右侧抽屉（1060px）。

**抽屉结构**
1. **订单明细摘要**（v1.3 改为接口字段口径，v1.6 补订单提交时间）：省平台订单号、采购计划单号、订单提交时间、订单明细编号、订单明细状态、响应时间；下方整行展示响应原因。不含药品类字段。
2. **配送明细表**：配送明细编号、采购价格、发票号、发票代码、批号、有效期、配送数量、配送时间、收货数量、收货时间；表头附「共 N 次配送 · 累计配送 X · 累计收货 Y」。
3. 收货进度用色值辅助：收货数量 < 配送数量为橙色（部分收货），未回传收货数量显示灰色「—」，收货时间未回传显示「—」。

**空态**：未配送显示「暂无配送明细」；拒绝配送的明细补充「（该订单明细已拒绝配送）」。

**数据模型**（`PC_ORDERS` → `items[]`）
| 字段 | 说明 |
|---|---|
| `detailId` | 订单明细编号（主键，配送明细挂靠此值） |
| `responseTime` / `responseReason` | 响应时间 / 响应原因 |
| `shipments[]` | 配送明细数组，字段：`shipId`（配送明细编号）、`price`（采购价格）、`invoiceNo`（发票号）、`invoiceCode`（发票代码）、`batchNo`（批号）、`expiry`（有效期）、`qty`（配送数量）、`shipTime`（配送时间）、`recvQty`（收货数量）、`recvTime`（收货时间） |

> 累计数量由明细数组实时汇总（`PC.shipStats`），不单独存冗余字段，避免配送明细与合计不一致。
